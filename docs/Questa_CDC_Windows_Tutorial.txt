Static Analysis

  Questa CDC static analysis performs the following structural verification tasks:
       · Identifies the design's clock structure: clock domains, clock gating, dividers, and so on.
       · Identifies the design's clock domain crossing signals.
       · Identifies the synchronization schemes on clock domain crossings.
       · Checks synchronization schemes' structures.

  Fine-tune CDC analysis to achieve better analysis by providing additional information that
  guides the analyzer. For example, supply information on clock groups, preferred
  synchronization types, exceptions, and other options. Following analysis, use the GUI
  debugging environment to debug problems found by CDC analysis.
  After you set up CDC analysis to perform properly, run CDC analysis, and then review the CDC
  analysis results. For each reported CDC issue (caution or violation), either set Status to waive or
  otherwise group issues (indicating the issues were reviewed and appropriately categorized for
  your development and verification processes), or modify the design to fix bugs.
  This tutorial (\examples\design_solutions\tutorials\cdc_static) runs Questa CDC static analysis
  (Figure 2-2) on the demo design.

                                                                                                    Set Up the CDC Environment

Set Up the CDC Environment

  CDC analysis setup uses Questa Formal-based Technology Tcl directives to configure the
  environment. CDC analysis performs many configuration steps automatically. For example,
  CDC analysis automatically infers clock and reset domains. Fine-tuning the configuration is
  typically needed to set up the entire environment correctly.
  Use Tcl directives to set preferential attributes for the CDC analysis run. Typically, use Tcl
  directives for these tasks:

       · Define clock domains.
       · Group synchronous clocks (or clocks related by gating logic) in one domain.

       · Change the clock groups inferred for particular ports.

       · Set selected test signals and configuration registers to constant values for the analysis.
  The file qs_files/directives.tcl (Figure 2-4) specifies such directives for this tutorial:

                                       Figure 2-4. Tcl Directives File

        # Define clocks
        netlist clock cpu_clk_in -period 50
        netlist clock core_clk_in -period 60
        netlist clock mac_clk_in -period 50

        # Define constants
        netlist constant scan_mode 1'b0

        # Add CDC constraints
        cdc scheme on -fifo -handshake

        #Uncomment to enable reconvergence
        # cdc reconvergence on
        # cdc preference reconvergence -depth 1 -divergence_depth 1
        cdc scheme on -fifo -handshake

  For the initial setup, the directives file contains these directives:

       · netlist clock
           Specifies clocks with their characteristics; redefines the clock domains and sets clock
           groups. You must specify a clock signal pattern that matches at least one clock signal.
           Conflicting netlist clock directives obey the last-one-wins rule. The -period value option
           specifies the clock period in time units (used to calculate parameters for promoted
           protocol assertions).

       · netlist constant
           Keeps the given variable at the specified constant value for CDC analysis. This netlist
           constant directive sets the scan_mode input signal to 0, which disables the scan mode
           logic.

       · cdc scheme on
           Turn on CDC analysis schemes. The -fifo option turns on detailed analysis of FIFO
           synchronization schemes. The -handshake option identifies HANDSHAKE
           synchronization schemes.

       · cdc reconvergence on
           Turn on reconvergence checking for all clock domains.

       · cdc preference reconvergence
           Sets analysis parameters for reconvergence schemes.
           The -depth depth option is the maximum sequential reconvergence depth for reporting
           reconvergence and single-source reconvergence CDC schemes. The default
           reconvergence depth is 0, which corresponds to combinational reconvergence. This
           tutorial uses a reconvergence depth of 1. In this case, CDC analysis only detects
           reconverging values if they reconverge within one cycle from the cycle in which the
           values are received.
           The -divergence_depth depth enables single-source reconvergence reporting and sets the
           divergence depth. By default, single-source reconvergence schemes are reported only as
           reconvergence schemes.

       · cdc scheme on
           Turn on complex CDC scheme checks.
           The -fifo option is to identify fifo crossings. Default: fifo schemes are reported as
           fifo_memory if the FIFO memory is valid. Otherwise, memory_sync or multi_bits
           scheme is reported.
           The -handshake enables identifying handshake crossings. Default: handshake schemes are
           reported as dmux or multi_bits schemes.

  Environment setup typically includes creating directives as described above. With the directives
  included, begin the tutorial by generating a clock report and then fine-tune the environment
  setup.

Run CDC Setup

CDC setup is the starting point when preparing your design for CDC analysis. The command
analyzes the design data and reports clocks, resets, and port domain information. It generates a
CDC setup report (cdc.rpt) and CDC database (cdc.db) that includes the setup information. You
can use the report or view the database in the GUI mode to review the CDC setup information.

Procedure

    1. Compile the HDL design source code.

                      prompt> cd C:\tutorials\cdc_static
                      prompt> run_batch compile_vl

The compile_vl makefile target compiles the design by running this command sequence:

vlib work                              Done implicitly

vmap work work                         Done implicitly

vlog -f qs_files/filelist_vl

    The vlib command creates an initial design library and sets access to design units in the
    library. The default working design library is: work. The vmap command creates a
    logical-to-physical mapping for the design library. The vlog command compiles the
    Verilog source code into the design library. Subsequent vlog invocations (without the
    vlib step) incrementally compile the Verilog portion of the design. In this tutorial, you
    must recompile the entire design whenever adjustments are made. Arguments are case
    sensitive.

2. Run the CDC analyzer and clock report generation.

                prompt> run_batch setup

The clock run_batch.bat target runs a CDC analyzer batch session (qverify -c -do):

                qverify -od Output_Results -c -do ^" ^
                     do qs_files/directives.tcl; ^
                     cdc setup -d demo_top; ^
                     cdc generate report cdc_detail.rpt; ^
                     exit^"

The -od option sets the initial output directory for the session; the -c argument selects
batch mode, and the -do argument specifies the script to execute.

The batch script starts by interpreting the directives.tcl file directives. The do Questa
Formal-based Technology Tcl command is similar to the standard source Tcl command,
with some enhancements. Next, the cdc setup executable Tcl command compiles the
design and infers clock domain information along with potential constraints for CDC
analysis.

Unless overridden by a -work argument to cdc setup, the CDC analyzer assumes the work

Modify CDC Constraints

  In addition to adjusting clock tree attributes, Questa Formal-based Technology Tcl directives
  provide a way to fine-tune CDC analysis by adjusting other nonclock related attributes.

   Here are some examples of nonclock related attributes you can use to fine-tune CDC analysis:

      · Use netlist blackbox to force CDC analysis to treat a module as a black box.

           CDC only understands synthesizable RTL code, so it infers unsynthesizable elements
           (and blocks for which no RTL is available) as black boxes. Sometimes you want to mark
           some design units--such as parent modules of unsynthesizable code--to be considered
           as user-defined black boxes. For example, you might identify as a user-defined black
           box a behavioral memory for which you do not want to perform clock analysis. Ports of
           an (inferred or user-defined) black box must be assigned port domains with the netlist
           port domain directive.

      · Use cdc custom sync to identify a synchronizer circuit model with custom logic.
           Some instances of synchronizer cells are not automatically recognized as proper
           synchronizers by CDC analysis. But if a synchronizer's cell model is identified as a
           custom synchronizer, CDC analysis reports that the signals driving the synchronizer's
           asynchronous input ports are synchronized properly. Like a black box module, ports of a
           custom synchronizer model must be assigned port domains with the netlist port domain
           directive.

      · Use cdc signal to change inferred signal types.

           CDC analysis classifies each CDC signal to identify the type of synchronization scheme
           it needs. For example, data signals typically require different synchronization than
           control signals; stable signals do not require synchronization, and so on. By overriding
           the signal type, you can control its proper synchronization scenarios.

                        prompt> run_batch compile_vl

            Compiling the HDL source code is required only if you made modifications since you
           ran the clock report generation.
       2. Run CDC analysis.

                        prompt> run_batch cdc

           The cdc run_batch.bat target runs a CDC analyzer batch session (qverify -c -do):

                                   qverify -c -od Output_Results -do ^" ^

       3. Check the CDC analysis results.
            The last part of the session output--and cdc.rpt shows a summary of the CDC analysis
           results (Figure 2-8). The summary lists these result categories:
           · Violations -- Must-fix synchronization problems.
           · Cautions -- Proper complex synchronization structures that require further analysis.
           · Evaluations -- Properly synchronized crossings.
           · Waived -- Crossings considered reviewed and OK (at least temporarily).

Review Synchronization Violations

  Synchronizer violations on clock domain crossing signals are must-fix violations. Synchronizer
  violations can occur for various reasons. A bug can cause improper synchronization of the
  signal. Add proper synchronization logic to the crossing to resolve bugs.
  Another undetected synchronizer violation can occur when the synchronization logic follows a
  FIFO scheme. Specify cdc scheme on -fifo to enable detection of the synchronizer.
  Sometimes, a signal can be properly synchronized, but was not detected by CDC analysis
  because a custom synchronizer synchronizes the signal. Specify the cdc synchronizer custom
  directive to fix such synchronization issues.
  Some CDC signals are intrinsically synchronized. You can waive these missing synchronizer
  violations as explained in "Waive CDC Results" on page 00. For specific synchronizer issues,
  reference the Questa CDC User Guide.

Potential Issues

  CDC netlist synthesis can uncover potential design elaboration or simulation issues that might
  not be flagged by the design compilation step For example, a process in the design with missing a
  signal in its sensitivity list may cause a difference between simulation and implementation.
  Therefore, it is recommended to clean up as many of these issues as possible.

Unresolved Modules

  The netlist synthesis sometimes return an Unresolved module warning.

# Message Summary

# -----------------------------------------------------------

# Count Type Message ID               Summary

# -----------------------------------------------------------

#3    Warning elaboration-702 Incomplete sensitivity-list.

#1    Warning parser-278              Ignoring unsupported construct.

# 10  Warning parser-285              Vopt warning.

#7    Warning parser-47               Unresolved module.

An unresolved module/entity is one for which no module or entity/architecture definition is
present. If a component declaration is present, the port directions are derived from that
declaration. Otherwise, the port directions are inferred from the connected logic. (If a port

Questa® CDC Windows Tutorial v2023.3
CDC Static in GUI Mode
Running Clock Analysis

direction cannot be inferred, the port direction is assumed to be INOUT). For Questa CDC,
unresolved modules are treated as unused or undriven logic, which means that they may affect
your CDC analysis.

The solution is to find the unresolved modules and include them in your vcom or vlog compile
command. Even if the modules or entities contain non-synthesizable constructs (such as RAM
model or FPGA vendor behavioral model), compiling and including them removes the issue
with the unresolved module and allows Questa CDC to infer the appropriate port directions and
connections from the module.

Black-boxed modules

  Another issue that must be closely tracked is black boxing of a design entity or module. When a
  module is black boxed, its internal logic is treated as unknown, including the connectivity
  between its inputs and outputs. This can mask some CDC issues so it is important to examine
  the cause of the black boxing. If a black boxed component does not connect to multiple clock
  domains, then having a black box component may not be a concern. However, sometimes
  multi-clocked components, such as FIFOs may not be fully recognized, and if they are black
  boxed then the CDC analysis might report false issues. In such a case, a CDC directive can be
  used (for example, cdc fifo). For more information on FIFO handling, see the Running Questa
  CDC & Questa AutoCheck on FPGA Designs AppNote.On the other hand, sometimes it is
  necessary to intentionally black box a component due to an encrypted vendor IP, a component
  you do not have access to, or a high-level behavior model. To intentionally black box a
  component by creating an HDM abstract model, select the object in the Design tab, right-click
  and choose Add Directive > netlist blackbox.

If the tool encounters an unsupported top-level construct in the top module, it can flag the
following error:

# Message Summary

# -----------------------------------------------------------

# Count Type Message ID Summary

# -----------------------------------------------------------

#1  Error hdl-94                      Top level design is black-boxed.

In this scenario, the processing will abort as there is nothing to examine if the top module is
black boxed.
