CDC Static Set Up the CDC Environment
Set Up the CDC Environment
CDC analysis setup uses Questa Formal-based Technology Tcl directives to configure the environment. CDC analysis performs many configuration steps automatically. For example, CDC analysis automatically infers clock and reset domains. Fine-tuning the configuration is typically needed to set up the entire environment correctly. Use Tcl directives to set preferential attributes for the CDC analysis run. Typically, use Tcl directives for these tasks:
· Define clock domains.
· Group synchronous clocks (or clocks related by gating logic) in one domain.
· Change the clock groups inferred for particular ports.
· Set selected test signals and configuration registers to constant values for the analysis.
The file scripts/directives.tcl (Figure 2-4) specifies such directives for this tutorial:
Figure 2-4. Tcl Directives File
# Define clocks netlist clock cpu_clk_in -period 50 netlist clock core_clk_in -period 60 netlist clock mac_clk_in -period 50
# Define constants netlist constant scan_mode 1'b0
# Add CDC constraints cdc scheme on -fifo -handshake
#Uncomment to enable reconvergence # cdc reconvergence on # cdc preference reconvergence -depth 1 -divergence_depth 1
For the initial setup, the directives file contains these directives:
· netlist clock
Specifies clocks with their characteristics; redefines the clock domains and sets clock groups. You must specify a clock signal pattern that matches at least one clock signal. Conflicting netlist clock directives obey the last-one-wins rule. The -period value option specifies the clock period in time units (used to calculate parameters for promoted protocol assertions).
· netlist constant
Keeps the given variable at the specified constant value for CDC analysis. This netlist constant directive sets the scan_mode input signal to 0, which disables the scan mode logic.

· cdc scheme on
Turn on CDC analysis schemes. The -fifo option turns on detailed analysis of FIFO synchronization schemes. The -handshake option identifies HANDSHAKE synchronization schemes.
· cdc reconvergence on
Turn on reconvergence checking for all clock domains.
· cdc preference reconvergence
Sets analysis parameters for reconvergence schemes.
The -depth depth option is the maximum sequential reconvergence depth for reporting reconvergence and single-source reconvergence CDC schemes. The default reconvergence depth is 0, which corresponds to combinational reconvergence. This tutorial uses a reconvergence depth of 1. In this case, CDC analysis only detects reconverging values if they reconverge within one cycle from the cycle in which the values are received.
The -divergence_depth depth enables single-source reconvergence reporting and sets the divergence depth. By default, single-source reconvergence schemes are reported only as reconvergence schemes.
Environment setup typically includes creating directives as described above. With the directives included, begin the tutorial by generating a clock report and then fine-tune the environment setup.

· A netlist constant directive is specified for the port or the signals driven combinationaly by the port.

· The port is identified as stable (with cdcsignal).

Modify CDC Constraints
In addition to adjusting clock tree attributes, Questa Formal-based Technology Tcl directives provide a way to fine-tune CDC analysis by adjusting other nonclock related attributes.
Here are some examples of nonclock related attributes you can use to fine-tune CDC analysis:
· Use netlist blackbox to force CDC analysis to treat a module as a black box.
CDC only understands synthesizable RTL code, so it infers unsynthesizable elements (and blocks for which no RTL is available) as black boxes. Sometimes you want to mark some design units--such as parent modules of unsynthesizable code--to be considered as user-defined black boxes. For example, you might identify as a user-defined black box a behavioral memory for which you do not want to perform clock analysis. Ports of an (inferred or user-defined) black box must be assigned port domains with the netlist port domain directive.
· Use cdc custom sync to identify a synchronizer circuit model with custom logic.
Some instances of synchronizer cells are not automatically recognized as proper synchronizers by CDC analysis. But if a synchronizer's cell model is identified as a custom synchronizer, CDC analysis reports that the signals driving the synchronizer's asynchronous input ports are synchronized properly. Like a black box module, ports of a custom synchronizer model must be assigned port domains with the netlist port domain directive.
· Use cdc signal to change inferred signal types.

CDC analysis classifies each CDC signal to identify the type of synchronization scheme it needs. For example, data signals typically require different synchronization than control signals; stable signals do not require synchronization, and so on. By overriding the signal type, you can control its proper synchronization scenarios.

Reconvergence analysis is not turned on by default to improve overall performance of CDC analysis. Without reconvergence, CDC analysis continues, but does not create a reconvergence model or report reconvergence crossings. To include reconvergence analysis, use both the cdc reconvergence on directive to turn on reconvergence analysis for selected clock domains and the cdc preference reconvergence directive to control reconvergence analysis parameters. Reference these commands in the TCL Commands section of the Questa Functional Verification Command Reference.
· Warning hdl-289 Missing clock domain for reset port.
Clock domain is not specified for the reset port. By default, a port is associated with the clock domain of the register to which it directly connects. Use netlist port domain to explicitly specify the clock domain for the reset port.

Review Synchronization Violations
Synchronizer violations on clock domain crossing signals are must-fix violations. Synchronizer violations can occur for various reasons. A bug can cause improper synchronization of the signal. Add proper synchronization logic to the crossing to resolve bugs. Another undetected synchronizer violation can occur when the synchronization logic follows a FIFO scheme. Specify cdc scheme on -fifo to enable detection of the synchronizer.
Sometimes, a signal can be properly synchronized, but was not detected by CDC analysis because a custom synchronizer synchronizes the signal. Specify the cdc synchronizer custom directive to fix such synchronization issues.
Some CDC signals are intrinsically synchronized. You can waive these missing synchronizer violations as explained in "Waive CDC Results". For specific synchronizer issues, reference the Questa CDC User Guide.

Unresolved module.

An unresolved module/entity is one for which no module or entity/architecture definition is present. If a component declaration is present, the port directions are derived from that declaration. Otherwise, the port directions are inferred from the connected logic. (If a port direction cannot be inferred, the port direction is assumed to be INOUT). For Questa CDC, unresolved modules are treated as unused or undriven logic, which means that they may affect your CDC analysis.

The solution is to find the unresolved modules and include them in your vcom or vlog compile command. Even if the modules or entities contain non-synthesizable constructs (such as RAM model or FPGA vendor behavioral model), compiling and including them removes the issue with the unresolved module and allows Questa CDC to infer the appropriate port directions and connections from the module.

Black-boxed modules
Another issue that must be closely tracked is black boxing of a design entity or module. When a module is black boxed, its internal logic is treated as unknown, including the connectivity between its inputs and outputs. This can mask some CDC issues so it is important to examine the cause of the black boxing. If a black boxed component does not connect to multiple clock domains, then having a black box component may not be a concern. However, sometimes multi-clocked components, such as FIFOs may not be fully recognized, and if they are black boxed then the CDC analysis might report false issues. In such a case, a CDC directive can be used (for example, cdc fifo). For more information on FIFO handling, see the Running Questa CDC & Questa AutoCheck on FPGA Designs AppNote.On the other hand, sometimes it is necessary to intentionally black box a component due to an encrypted vendor IP, a component you do not have access to, or a high-level behavior model. Chapter 4 CDC Protocol
CDC protocol verification checks that subcircuits that span clock domain boundaries do not (or cannot) violate certain expected timing properties of the clock domain crossing logic. CDC protocol verification starts off where static CDC analysis ends. CDC protocol checkers verify that crossing logic either avoids, or tolerates, metastability effects caused when data timed in transmit clock domains propagate to logic timed in other asynchronous clock domains. A process called CDC protocol promotion creates these checkers, binds them to the design and generates working environments for running protocol verification. Figure 4-1 shows the parallel analyses that comprise the standard CDC protocol verification flow: formal analysis with protocol properties, and simulation with protocol assertions and cover groups.

Proofs vs Firings
The flow described in this procedure uses no formal assumptions (i.e., constraints). With such a formal analysis setup, there can be no false proofs. That is, all proofs are valid proofs: their assertions cannot fail. Adding more assumptions does not invalidate any proven assertions.
Alternatively, counterexamples found by formal analysis (i.e., firings) can be false firings. It might be possible to add legal formal assumptions to the setup and actually turn some firings into proofs. That is, a counterexample might use an illegal stimulus sequence to violate its assertion.

Chapter 5 CDC-FX
CDC-FX verification verifies that the compiled design violates certain expected timing properties of the clock domain crossings when the design is extended with CDC-FX metastability injection logic. Dynamic CDC analysis has two distinct phases:
1. Simulation with CDC protocol assertions
2. Simulation with CDC-FX metastabilityinjection
Simulation tests, which were used for simulation with CDC protocol assertions, can be reused for CDC-FX metastability analysis. For these simulations, the compiled design is extended with CDC-FX metastability injection logic, which causes the simulated design to behave like a hardware implementation with random metastability effects. End-to-end tests that pass under normal simulation can fail when simulated with metastability effects, unless the design is metastability hardened.
For the dynamic CDC analysis, you first run the CDC protocol assertion step, followed by the CDC-FX phase. A well-constructed test suite simulated with metastability effects detects unhardened CDC paths and logic by producing end-to-end test failures. You can debug the test failures the same way as with standard simulation, by analyzing backward from the miscompared outputs using your simulation waveforms and debug environment.
The CDC-FX Tutorial guides you through the standard FX verification flow and demonstrates the basic concepts of this verification process.

Chapter 6 CDC Hierarchical Top-down Analysis

The best choice for analyzing large, complex designs, CDC hierarchical analysis can analyze designs with many clocks and clock domain crossings while achieving better performance and clearer results, and using less memory. The CDC hierarchical analysis methodology supports both top-down and bottom-up flows. This section focuses on CDC hierarchical top-down analysis, which can be run to reveal top-level CDC issues before the block-level design is fully developed. This capability makes CDC hierarchical top-down analysis especially advantageous for SoC and IP designs to discover CDC top-level issues before the blocks are fully developed. Using CDC hierarchical top-down analysis requires only the top-level design, the top-level constraints, and the list of blocks.
Generally, the SoC integration team includes the hierarchical databases for the IP blocks. The hierarchical block databases abstract the intra-block design information, so the SoC integration team can focus on top-level inter-block CDC results.
CDC hierarchical top-down analysis generates and uses a hierarchical data model (HDM) to communicate necessary block-level internal information required to detect CDC issues at the top level during top-down analysis. An HDM is the binary, hierarchical database that contains all the information about the block internals that CDC analysis requires to detect CDC issues in the top-level analysis. Unlike black boxes, HDMs are sometimes called white boxes because CDC crossings within HDMs are visible, giving the HDMs transparency compared to black boxes that only expose ports. An HDM is a concise, portable abstract model that captures the CDC intent of a block. An HDM for each specified block is generated automatically during block-level analysis, the first step in CDC hierarchical top-down analysis.
Note Hierarchical CDC analysis is static analysis only; it does not promote protocol assertions or generate CDC-FX injectors.

Chapter 7 CDC Hierarchical Bottom-up Analysis
CDC hierarchical bottom-up analysis is ideal for IP-based SoCs. Typically the IP in an IP-based SoC flow is available before the top-level design and setup. The IP groups run block-level CDC analysis and generate abstract block models (HDMs) that they then deliver to the integration team who uses the HDMs in the top-level CDC analysis. In this bottom-up flow, the IP team must also generate the block-level constraints because the block-level constraints are not automatically generated.
Prerequisites for CDC hierarchical bottom-up analysis include these tasks:
· CDC analysis setup has been completed on the IP-level design.
· Block-level CDC analysis setup must include both setup and clock analysis steps.
· Top-level constraints define the top-level clock and clock groups, as well as input and output port clock domains.
Typically, the top-level constraints are specified in SDC (synthesis design constraints) format with the SDC file imported into the hierarchical CDC hierarchical top-down analysis flow, and the CDC-specific directives are specified in a Tcl file. Alternatively, use Questa Tcl commands to specify both constraints and CDC-specific directives in a directives Tcl file.

RDC Analysis
RDC analysis performs extensive reset checking and analysis that addresses the proliferation of reset domains. In today's designs, the ever increasing complexity of reset signaling topologies almost assures that manual inspection and verification of reset domain will result in missed bugs. Independent reset domains created by complex reset sequences or reset structures can increase metastability and signal reconvergence issues similar to the failures seen in asynchronous clock domain crossings (CDC). The resulting metastability introduced by such reset structures cannot be modeled by simulation, which also considerably increases the risk of unpredictable chip behavior when samples return from the fab. RDC finds such violations early in the design process and provides extensive feedback that helps you debug such issues, saves time, increases productivity, and substantially reduces risk.
Using RDC, you can determine reset characteristics:
· What synchronous and asynchronous resets are in the design
· Whether the reset tree is correct
· What reset domains reset registers in the design
· Whether data paths cross reset domains
· Whether reset is used in data
· Whether the metastability in reset domain crossings fall within acceptable tolerances
Reset domain checks essentially extend CDC analysis for reset. Run CDC analysis before running RDC. Review and ensure clock groups are correct. Then run RDC to do reset analysis and checks.

Order Resets to Reduce Metastability
Based on your analysis review and results, you may order resets with ordering directives to avoid some violations and reduce metastability issues for asynchronous resets.
If your design has instances in which the source flop is reset asynchronously, but the destination flop is not reset, metastability can occur because a signal is driven by a reset in one domain and the destination is d riven by a reset in another domain. RDC supports reset ordering directives, the rdc order assert directive and the rdc order deassert directive to assert and deassert sequences for such resets. These reset ordering directives analyze reset domain crossings with respect to the reset domains of the source and destination sequential elements, and then generate corresponding ordered schemes. Using these directives and reset ordering constraints to plan the assertion order of the reset signals, the destination flop can be held in the reset state before asserting the signal. If the assertion order holds and the deassertion order is also compliant--the RDC path is considered functionally valid.

RDC Tutorial Conclusions
In this tutorial you learned how to run RDC analysis and to use filters and status to manage and track issues across analysis runs. Using RDC and these techniques on your own designs, you can see how RDC saves time and resources by helping you resolve reset issues early in the development and verification processes and decreases the risk of post silicon behavioral issues due to metastability or recovergence.
